# MedAudit upgrade review

Reviewed 2026-11-27 at upstream commit `d68792b`.

This is a source review and environment check. Findings described as static
inferences below have not been confirmed through running the API.

## Existing strengths worth preserving

- Two distinct service factories separate staff access from audit verification.
- The logging engine combines authenticated encryption, per-record key evolution,
  hash chaining, authenticated anchors, and auditor checkpoints.
- Hospital authorization considers both role and patient assignment.
- Existing emergency grants are patient-scoped and expire.
- Patient data operations attempt to fail closed when auditing is unavailable.
- Tests already cover tampering, rollback, role checks, and concurrent activity.

Adding ordinary CRUD screens would contribute less than completing the response
to a security event: detect it, investigate it, record a review, export evidence.

## Findings

### 1. Generated secrets and data are tracked

Evidence: `git ls-files data` includes `data/auditor/root.keys`,
`data/auditor/console_root.keys`, `data/auditor/auditors.json`, the hospital
database, audit logs, and current chain-state keys. `git ls-files '*pyc'` also
lists generated bytecode. `.gitignore` contains only `.venv/`.

Impact: these published keys cannot provide secrecy for the bundled records.
The bundled database also makes `run.py --demo` skip initialization because the
database already exists. A demonstration should generate independent keys on
each new install and explicitly use synthetic data.

Remedy: remove generated state from future tracked files, expand ignore rules,
document fresh initialization, and treat any genuine credentials that ever used
these values as exposed. Removing files does not remove them from Git history.
Do not rewrite remote history as part of this upgrade.

### 2. Native Windows cannot import the audit engine

Evidence: `medaudit/auditlog/core.py:21` imports `fcntl` unconditionally. Exclusive
and shared `flock` calls are used for writer and verifier coordination. POSIX
permission checks occur throughout the engine and its tests.

The local runtime check returned `Platform: Windows` and
`fcntl available: False`. Python documents this module as Unix-only:
<https://docs.python.org/3/library/fcntl.html>.

Remedy: offer a reproducible Linux container/WSL path first, or implement and test
Windows file locking and ACL enforcement deliberately. Removing locking or
skipping permission enforcement would weaken the security demonstration.

### 3. Input constraints run before trimming

Static evidence: `PatientIn` at `medaudit/hospital/app.py:41` accepts a nonempty
string, but the handler stores `body.name.strip()` at line 218. `BreakGlassIn`
at line 53 checks raw length, then the handler logs and stores a stripped reason
at lines 290–293. The date constraint checks format, not calendar validity.

Inference: a whitespace-only value can meet raw length checks and then become
empty; a formatted but impossible date can pass the regular expression.

Remedy: normalize and validate at the request boundary; add focused negative
tests for blank names/reasons and invalid dates.

### 4. Auditor session creation precedes successful audit

Static evidence: `medaudit/auditor/app.py:165` inserts the session into the
in-memory dictionary, then line 166 calls `clog`, which can raise HTTP 503.

Inference: an audit failure leaves a server-side session entry even though the
response does not release the new token. This is an inconsistent fail-closed
ordering; this review does not claim the caller receives or can guess the token.

Remedy: complete required auditing before persisting the authenticated session,
and test that audit failure leaves session state unchanged.

### 5. Automatic verification failures are silent

Static evidence: `scheduler` at `medaudit/auditor/app.py:91` catches all exceptions
and executes `pass` at lines 99–100.

Impact: key, checkpoint, or filesystem failures can suppress automatic checks
without an operational explanation. This is distinct from a normal scan that
returns a detected-tampering result.

Remedy: expose sanitized failure status and log the failed operation without
secrets or patient data; test the background-failure path.

### 6. Browser defense can be strengthened

Evidence: both static UIs store bearer tokens in `sessionStorage`. Both services
allow `script-src 'self' 'unsafe-inline'`; the UI contains inline scripts and
some inline event handlers.

Impact: any future script-injection defect would have access to the token, and
inline CSP permission provides less protection than external same-origin script
files. This review has not demonstrated a working XSS exploit; many existing
template values are escaped.

Remedy: externalize scripts, remove inline handlers, tighten CSP, and specify a
deliberate session design. Cookie authentication would also require CSRF controls.

### 7. Engineering evidence and repeatability are incomplete

Evidence: `requirements.txt` declares only lower bounds, includes test packages
with runtime packages, and has no matching lockfile. No tracked `.github`
workflow was found. The README explains the security mechanisms but there is no
SRS, STRIDE model, ADR collection, or requirement-to-test traceability matrix.

Remedy: validate and pin a compatible dependency set; add CI and the engineering
deliverables described in the capability map. Retain and extend the original
tests rather than replacing them with screenshots or documentation claims.
